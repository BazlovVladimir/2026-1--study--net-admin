# Цель работы

Настроить взаимодействие через сеть провайдера посредством статической маршрутизации локальной сети организации с сетью основного здания, расположенного в 42-м квартале в Москве, и сетью филиала, расположенного в г. Сочи.

# Выполнение

## Настройка взаимодействия локальной сети организации с сетью основного здания в 42-м квартале через сеть провайдера

1. В Cisco Packet Tracer была собрана расширенная сетевая топология организации.  
   В схеме присутствуют локальные сети подразделений, сеть провайдера, маршрутизаторы, коммутаторы, повторители, серверы и рабочие станции.  
   Центральная сеть организации соединяется с сетью провайдера, через которую должно быть обеспечено взаимодействие с основным зданием, расположенным в 42-м квартале Москвы, а также с филиалом в г. Сочи.

   На схеме отображены основные сетевые узлы:

   - центральный шлюз организации **msk-donskaya-vabazlov-gw-1**;
   - шлюз здания в 42-м квартале **msk-q42-vabazlov-gw-1**;
   - коммутаторы локальных сетей;
   - сеть провайдера **provider-vabazlov**;
   - отдельные VLAN для связи с удаленными сетями;
   - рабочие станции и серверы.

   ![Общая схема сети организации и подключенных удаленных сегментов](Screenshot_1.png){ #fig:001 width=80% }

2. На коммутаторе провайдера **provider-vabazlov-sw-1** была выполнена настройка транковых соединений.  
   Для передачи трафика нескольких VLAN через одну физическую линию интерфейсы **FastEthernet0/3** и **FastEthernet0/4** переведены в режим trunk.

   Также на коммутаторе провайдера были созданы VLAN для разделения каналов связи:

   - **VLAN 5** — сеть для взаимодействия с объектом в 42-м квартале, имя VLAN: **q42**;
   - **VLAN 6** — сеть для взаимодействия с филиалом в Сочи, имя VLAN: **sochi**.

   После создания VLAN были активированы интерфейсы VLAN 5 и VLAN 6 с помощью команды `no shutdown`.  
   Выполненная конфигурация была сохранена в энергонезависимую память командой `wr mem`.

   ![Настройка VLAN и транковых портов на коммутаторе провайдера](Screenshot_2.png){ #fig:002 width=80% }

3. На центральном шлюзе организации **msk-donskaya-vabazlov-gw-1** были настроены подинтерфейсы для работы с VLAN, проходящими через сеть провайдера.

   Для связи с сетью 42-го квартала создан подинтерфейс:

   - интерфейс: **FastEthernet0/1.5**;
   - VLAN: **5**;
   - тип инкапсуляции: **IEEE 802.1Q**;
   - IP-адрес: **10.128.255.1**;
   - маска: **255.255.255.252**;
   - описание: **q42**.

   Для связи с филиалом в Сочи создан подинтерфейс:

   - интерфейс: **FastEthernet0/1.6**;
   - VLAN: **6**;
   - тип инкапсуляции: **IEEE 802.1Q**;
   - IP-адрес: **10.128.255.5**;
   - маска: **255.255.255.252**;
   - описание: **sochi**.

   Также на маршрутизаторе были добавлены статические маршруты:

   - маршрут к сети **10.129.0.0/16** через следующий узел **10.128.255.2**;
   - маршрут к сети **10.130.0.0/16** через следующий узел **10.128.255.6**.

   Это обеспечивает передачу трафика из центральной сети организации в сторону сети 42-го квартала и филиала в Сочи через сеть провайдера.

   Дополнительно подинтерфейсы были отмечены как внутренние для NAT командой `ip nat inside`.  
   Для NAT был создан расширенный список доступа **nat-inet**, в котором разрешены отдельные хосты из сетей организации:

   - **10.129.0.200**;
   - **10.129.128.200**;
   - **10.130.0.200**.

   После завершения настройки конфигурация была сохранена командой `wr mem`.

   ![Настройка подинтерфейсов, статических маршрутов и NAT на центральном шлюзе](Screenshot_3.png){ #fig:003 width=80% }

4. На маршрутизаторе основного здания в 42-м квартале **msk-q42-vabazlov-gw-1** была настроена связь с центральным шлюзом через VLAN 5.  
   Для этого создан подинтерфейс **FastEthernet0/1.5**, использующий инкапсуляцию **dot1q 5**.

   Параметры подинтерфейса:

   - интерфейс: **FastEthernet0/1.5**;
   - VLAN: **5**;
   - IP-адрес: **10.128.255.2**;
   - маска: **255.255.255.252**;
   - описание: **donskaya**.

   Для локальной сети основного здания был создан подинтерфейс **FastEthernet0/0.201**:

   - VLAN: **201**;
   - IP-адрес: **10.129.0.1**;
   - маска: **255.255.255.0**;
   - описание: **q42-main**.

   Для сети управления был создан подинтерфейс **FastEthernet1/0.202**:

   - VLAN: **202**;
   - IP-адрес: **10.129.1.1**;
   - маска: **255.255.255.0**;
   - описание: **q42-management**.

   Далее была настроена статическая маршрутизация.  
   В качестве маршрута по умолчанию указан центральный шлюз организации:

   - **0.0.0.0/0 → 10.128.255.1**.

   Также был добавлен маршрут к сети здания общежития:

   - **10.129.128.0/17 → 10.129.1.2**.

   Эта настройка позволяет маршрутизатору 42-го квартала передавать неизвестный трафик в сторону центральной сети, а трафик к сети общежития направлять через отдельный шлюз управления.

   ![Настройка маршрутизатора 42-го квартала и статических маршрутов](Screenshot_4.png){ #fig:004 width=80% }

5. На коммутаторе **msk-q42-vabazlov-sw-1** была выполнена настройка портов для подключения локальной сети 42-го квартала.

   Интерфейс **FastEthernet0/24** был переведен в режим trunk, так как через него передается трафик VLAN между сетевыми устройствами.

   Интерфейс **FastEthernet0/1**, к которому подключена рабочая станция, был настроен как access-порт и помещен в VLAN 201:

13. После настройки маршрутизаторов, коммутаторов и рабочих станций была выполнена проверка доступности удаленных узлов с компьютера **admin-donskaya-vabazlov-1**.

   Результаты проверки показали:

   - связь с узлом **10.129.0.200** установлена;
   - связь с узлом **10.129.128.200** установлена;
   - связь с узлом **10.130.0.200** установлена.

   Таким образом, передача трафика между центральной сетью организации, сетью 42-го квартала, сетью общежития и филиалом в Сочи работает корректно.

15. После настройки статической маршрутизации была выполнена проверка таблицы маршрутизации на центральном шлюзе организации **msk-donskaya-vabazlov-gw-1**.

# Контрольные вопросы

1. **Приведите пример настройки статической маршрутизации между двумя подсетями организации.**

   Статическая маршрутизация используется в том случае, когда администратор вручную указывает маршрутизатору, через какой следующий узел необходимо передавать пакеты в удалённую сеть.

   Например, в организации есть две подсети:

   - сеть главного офиса: **10.128.6.0/24**;
   - сеть филиала: **10.130.0.0/24**.

   Между ними находится сеть провайдера, через которую соединены два маршрутизатора.  
   На маршрутизаторе главного офиса адрес соединения с филиалом — **10.128.255.5**, а на стороне филиала — **10.128.255.6**.

   Чтобы маршрутизатор главного офиса знал путь к сети филиала, на нём можно добавить статический маршрут:

   `ip route 10.130.0.0 255.255.255.0 10.128.255.6`

   Данная команда означает, что весь трафик, предназначенный для сети **10.130.0.0/24**, необходимо отправлять на следующий маршрутизатор с адресом **10.128.255.6**.

   На маршрутизаторе филиала также необходимо указать обратный маршрут к сети главного офиса:

   `ip route 10.128.6.0 255.255.255.0 10.128.255.5`

   Эта команда сообщает маршрутизатору филиала, что пакеты к сети **10.128.6.0/24** нужно передавать через следующий узел **10.128.255.5**.

   В выполненной работе аналогичный принцип использовался для связи центральной сети организации с сетью 42-го квартала и филиалом в Сочи. Например, на центральном шлюзе были добавлены маршруты к сетям **10.129.0.0/16** и **10.130.0.0/16** через соответствующие маршрутизаторы удалённых площадок.

2. **Опишите процесс обращения устройства из одного VLAN к устройству из другого VLAN.**

   VLAN используется для логического разделения сети на отдельные широковещательные домены. Устройства, находящиеся в разных VLAN, не могут обмениваться данными напрямую на канальном уровне, даже если они подключены к одному коммутатору. Для взаимодействия между VLAN требуется маршрутизация.

   Процесс обращения устройства из одного VLAN к устройству из другого VLAN можно описать следующим образом.

   Сначала компьютер определяет, находится ли IP-адрес получателя в той же подсети. Для этого он сравнивает свой IP-адрес, маску подсети и адрес назначения. Если получатель находится в другой подсети, компьютер отправляет пакет не напрямую получателю, а на шлюз по умолчанию.

   Затем компьютер с помощью ARP-запроса определяет MAC-адрес своего шлюза. После получения ARP-ответа он формирует Ethernet-кадр, где MAC-адресом получателя указывается MAC-адрес шлюза, а IP-адрес назначения остаётся адресом конечного устройства.

   Коммутатор передаёт кадр в пределах VLAN, к которой относится порт отправителя. Если связь между коммутатором и маршрутизатором организована через trunk-порт, кадр передаётся с VLAN-тегом 802.1Q.

   На маршрутизаторе или L3-коммутаторе принимается кадр соответствующего VLAN. Устройство анализирует IP-адрес назначения, обращается к таблице маршрутизации и определяет, через какой интерфейс или подинтерфейс необходимо отправить пакет дальше.

   После этого маршрутизатор формирует новый Ethernet-кадр для VLAN получателя. В этом кадре уже используется MAC-адрес следующего устройства или конечного получателя, если он находится в напрямую подключенной сети. Далее пакет передаётся в нужный VLAN и доставляется адресату.

   В данной работе такой принцип использовался при настройке подинтерфейсов маршрутизаторов с инкапсуляцией **dot1q**. Например, на маршрутизаторе 42-го квартала были созданы подинтерфейсы для VLAN 201 и VLAN 202, а на маршрутизаторе филиала в Сочи — для VLAN 401 и VLAN 402.

3. **Как проверить работоспособность маршрута?**

   Работоспособность маршрута можно проверить несколькими способами.

   Основной способ — использование команды `ping`. Она отправляет ICMP-запросы на указанный IP-адрес и ожидает ICMP-ответы. Если ответы приходят, значит между устройствами есть сетевое взаимодействие.

   Например, для проверки доступности рабочей станции филиала можно выполнить команду:

   `ping 10.130.0.200`

   Если в ответ отображаются строки вида `Reply from 10.130.0.200`, значит узел доступен. Если отображается `Request timed out`, это может указывать на отсутствие маршрута, неправильную настройку шлюза, ошибку в IP-адресации, неработающий интерфейс или проблему с VLAN.

   Более подробную проверку можно выполнить с помощью команды `tracert` в Windows или `traceroute` в Unix-подобных системах. Эта команда показывает, через какие промежуточные маршрутизаторы проходит пакет до конечного узла.

   Например:

   `tracert 10.129.128.200`

   По результатам трассировки можно определить, на каком участке маршрута возникает проблема. Если трассировка доходит до конечного адреса, значит маршрут построен корректно.

   Также для диагностики можно использовать:

   - проверку таблицы маршрутизации;
   - проверку состояния интерфейсов командой `show ip interface brief`;
   - проверку VLAN на коммутаторах;
   - проверку trunk-портов;
   - проверку правильности шлюза по умолчанию на конечных устройствах.

   В выполненной работе работоспособность маршрутов была подтверждена с помощью команд `ping` и `tracert` между центральной сетью, сетью 42-го квартала, сетью общежития и филиалом в Сочи.

4. **Как посмотреть таблицу маршрутизации?**

   Таблица маршрутизации показывает, какие сети известны маршрутизатору и через какие интерфейсы или следующие узлы он передаёт трафик. В Cisco IOS таблицу маршрутизации можно посмотреть командой:

   `show ip route`

   В результате выполнения команды отображаются напрямую подключенные сети, статические маршруты, маршруты по умолчанию и маршруты, полученные с помощью динамических протоколов маршрутизации.

   Основные обозначения в таблице маршрутизации:

   - **C** — directly connected, напрямую подключенная сеть;
   - **L** — local, локальный адрес интерфейса маршрутизатора;
   - **S** — static, статический маршрут;
   - **S\*** — статический маршрут по умолчанию;
   - **R** — маршрут, полученный через RIP;
   - **O** — маршрут, полученный через OSPF;
   - **D** — маршрут, полученный через EIGRP.

   Например, запись:

   `S 10.130.0.0/16 [1/0] via 10.128.255.6`

   означает, что сеть **10.130.0.0/16** доступна через следующий узел **10.128.255.6**, а сам маршрут был задан вручную как статический.

   Маршрут по умолчанию обычно отображается в виде:

   `S* 0.0.0.0/0 [1/0] via 10.128.255.5`

   Он используется тогда, когда в таблице маршрутизации нет более точного маршрута к сети назначения.

# Заключение

В ходе работы была выполнена настройка взаимодействия локальной сети организации с сетью основного здания, расположенного в 42-м квартале Москвы, а также с сетью филиала в г. Сочи через сеть провайдера.

На маршрутизаторе 42-го квартала был настроен маршрут к сети общежития **10.129.128.0/17**, а также маршрут по умолчанию в сторону центрального шлюза. После настройки была выполнена проверка доступности узлов с помощью команды `ping`, а также проверка прохождения маршрутов с помощью команды `tracert`. Результаты проверки показали, что устройства из центральной сети организации, сети 42-го квартала, сети общежития и филиала в Сочи успешно взаимодействуют друг с другом. Таблицы маршрутизации содержат необходимые статические маршруты, а трассировка подтверждает прохождение пакетов через ожидаемые промежуточные маршрутизаторы.
